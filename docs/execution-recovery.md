# 执行器中断检测与提交检查点接续

## 触发与边界

- 新版执行器为每个进程生成独立会话 ID，通过心跳报告真实活跃任务；模型额度查询独立在线程中进行，不阻塞心跳。
- 有效活跃心跳仍包含任务时，无论阶段持续多久都不按超时误判。领取任务与下一次心跳之间有 120 秒保护窗口。
- 同一执行器 ID 的新会话不会抢占仍有有效工作心跳的旧会话；旧会话也不能继续调用新版执行器接口覆盖新会话的任务状态。
- 执行器上线并报告有效心跳后，每 20 秒核对一次自己的遗留活跃记录。离线时页面直接提示心跳缺失，不再只展示旧的“正在研发”输出。

## 可自动接续的检查点

审核类交付任务停在 `submitting`，所有变更仓库有已推送的冻结提交、隔离工作区和分支记录时，保留原任务 ID，排队为 `waiting_retry`，走独立的提交恢复入口，不调用研发模型。

恢复前逐仓核对本地 HEAD、已跟踪修改、仓库来源、远端分支与已有 PR，并确认 TFS 标题和正文没有改变。所有仓库检查通过前不创建第一个 PR。已存在 PR 按源/目标精确匹配；已完成且源提交一致的 PR 可复用，源分支删除不要求重新推送。已放弃、范围变化或无法唯一确认的 PR 不盲目重建。

新任务保存校验对应的提交指纹；旧检查点没有指纹时，只补做既定构建/校验。不会重新研发、创建提交、推送代码或重放业务 SQL。之后按原项目策略审核、监控合并、协调发版并交付。

## 不确定阶段

开发、合入目标分支后的本地构建、发布中等阶段，若无法确认远端副作用，不自动重放；明确记录执行器中断、原阶段和最后检查点，保留现场供核对，不继续假报运行。取消/回滚等用户控制优先，终态与其他执行器任务不受影响。

本机制不是通用的任意阶段事务回滚，也不把 TFS 状态“已解决”当成 PR/构建已经完成的证据。

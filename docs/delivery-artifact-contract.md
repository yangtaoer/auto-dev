# 研发交付产物契约

适用于所有项目、所有交付方式与旧任务策略快照；问题分析任务仍单独交付分析报告。

## 用户可见范围

- 业务系统包：本地构建的正式包，或已成功交付流水线的业务包产物页。
- SQL：本需求需要部署的建表、改表、索引、初始化、数据迁移/修复，以及必要的回滚脚本。
- 必要配置：配置文件、配置项合并模板；密码等值使用部署环境占位符。

没有 SQL/配置变更时不生成空文件。源码 XML、截图、测试程序、内部 JSON 校验清单、说明报告、菜单链接、License 申请不作为独立研发产物。菜单/权限说明仍保存在研发结果与验收项账本中。内部审计、构建和报告记录不删除。

## 收集与门禁

1. 项目预设和运行时策略统一允许 SQL/config，覆盖 APP 的旧白名单；SQL 同时支持仓库根目录及多层目录。
2. `delivery_assets` 按仓库和相对路径声明实际文件；自动识别 SQL、运行配置，同时排除源码 XML、测试目录、构建输出与 secrets。已存在但本次实际使用的迁移也可明确声明，不必为收集而改写历史文件。
3. 本地打包、审核后本地打包、审核后流水线发版都执行归集。进入最终交付时再次核对；沿本任务保存的文件集合归集，不能把其他并发需求合入目标分支的文件混进来。
4. DM7 写入调用在开始/结束时保存任务级调用 ID、用途、状态和 SQL 指纹；不保存原始 SQL、连接 ID或凭据，不导出全局 DM7 发布日志。失败或继续执行后仍核对历史调用。命令行数据库操作也必须在结构化结果中如实声明并保存业务脚本。
5. `database_changes` 将调用映射到业务 SQL 或有清理/回滚证据的临时验证。缺文件、空文件、越界路径、遗漏脚本声明进入现有原会话自动补齐流程，不新增管理员常规确认。
6. 页面、交付记录、邮件和 TFS 交付清单使用同一可见范围。内部验证 JSON 保留审计但不展示；业务包缺失不能用 README 冒充成功。

## 结果字段

`delivery_assets`: `repository`, `path`, `kind` (`sql`/`config`), `purpose`。

`database_changes`: `classification` (`business_change`/`temporary_verification`), `call_ids`, `script_paths`, `evidence`。多仓同名脚本应写仓库限定路径；临时验证须有清理或事务回滚证据。插件用途为 migration/production_change 的调用不可被临时验证分类跳过。

自动补齐只保存/修正脚本，不应再次执行已经完成的业务写入；数据库验证与实际部署仍遵循项目已有权限和交付流程。

历史上从未保存过的 SQL 无法凭空恢复；已归集但被审核模式隐藏的 SQL/配置会恢复显示。新任务执行完整性检查，继续中的旧任务在交付时补做文件归集。

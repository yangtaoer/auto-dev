## SC-TICKET-LOSS-001：用户确认的丢行复现

来源：用户于 2026-10-12 在排查操作票审核丢指令的会话中明确报告“我测出来了”，补充实际操作顺序。用户未提供此次测试的票号、运行环境、账号岗位或部署版本，不从其他测试档案补推这些信息。

1. 先写首尾两条指令，最终对应第 1、6 条。
2. 在中间插入四个新增空白行，对应第 2、3、4、5 条；填写单位和厂站，操作项目保持空白。
3. 触发一次自动保存。
4. 在同一页面补齐中间四行的操作项目。
5. 在下一次自动保存触发前送审。

用户确认的结果：审核时只剩原第 1、6 条，中间四条不见了。该记录属于用户业务实测反馈；代理没有连接业务数据库核验这张票，也没有执行业务界面操作。

## SC-TICKET-LOSS-ROOT-001：本地代码证据与隔离验证

代码核对范围：本地四川省调 `dcsd-direct-ui-sichuan` 委托票脚本 `src/main/resources/META-INF/resources/tbp_config/runtime/module/direct/dd/forms/wtcz_ylzxzb.form.js`，普通票脚本有同类逻辑；本地平台依赖为 `eomp-cloud-fvengine:1.0.23.7`。本地版本不是现场部署版本的证明。

- 委托票 `autoSubmitFormRewrite()` 在操作项目 `cznr` 为空时执行 `delete arr[i]`，从提交数组跳过该行，因此四个空白新增行没有入库。单位、厂站完整不改变这一判断。
- `np_autoSave()` 在保存返回成功后调用整个表格的 `grid.accept()`；已跳过的行也被清除 `_state = added` 标记。
- 补填操作项目时，MiniUI 把这些行标成 `modified`。送审调用 `submitFormRewrite()`，按该状态提交更新。
- 平台按 `_state` 区分插入和更新。`modified` 走按 `mxid` 的 UPDATE；四个明细主键对应的记录并不存在，更新影响零行。批量更新没有把每行影响数为零判为失败，表单接口仍返回更新成功。
- 送审前 `setZlxh()` 按页面六行重新编号，已存在的末行能更新到序号 6，因此可出现仅显示编号 1、6 的断号结果。

代理使用真实前端保存函数、MiniUI 编码和行状态函数，配合内存模拟后端更新规则完成隔离验证：补填前跨过自动保存的用例仅存储第 1、6 条，页面仍有六条且返回成功；第一次自动保存前全部填齐的对照用例存储六条。该验证没有访问业务库，不等同于业务环境端到端回归。

## SC-TICKET-LOSS-FIX-001：授权后的本地修复与验证

来源：2026-10-12 用户要求立即修复已复现的丢行问题，检查正预令二次编辑、审核编辑及其他同类保存场景，并要求指令联想框空结果不占空间、搜索结果去重。下述为代理对本地源码与隔离测试的观察，不代表业务环境复验或部署完成。

- 覆盖普通预令、委托预令、普通正令、委托正令、顺控票的 12 个完整保存方法及顺控排序保存入口。共享方法在 `dcsd-direct-ui-sichuan` 的 `direct/forms/directforms.js`。
- 获取提交快照使用 `mini.clone(changes, false)`。项目实际 MiniUI 的 clone 默认删除 `_state` 等字段，第二参数必须为 false，才能保留区分 INSERT、UPDATE、DELETE 的状态。回归测试直接执行项目 MiniUI 的 clone、编码和行状态函数，且验证了默认 clone 会删除状态。
- 完整保存成功后，只确认请求中实际提交的明细；过滤的空白新增行继续保持 added。同步已保存的业务字段，尤其是过滤空行后的序号；保护提交快照中的 removed 标记，清理已确认删除的 MiniUI 缓存。
- 委托正令自动保存原先引用本页没有定义的保存函数，改为已有编辑保存方法的自动保存模式，保持编辑状态和编辑人字段不变。没有新增自动保存的启动入口。
- 顺控编辑保存的旧表单 ID 误用普通正令 ID，已改为对应顺控表单；排序局部保存只更新已有行排序，不确认其他字段的修改、不提前插入空白新增行。
- 普通、委托正预令的操作项目联想共用搜索处理：空白及重复结果过滤；空列表 display:none；新输入、选择候选、编辑结束及跨行切换清理列表和未完成查询；过期成功/失败响应不会覆盖新结果；鼠标选择候选保留编辑器焦点。
- 用户既有的普通拟票 20 秒、二次编辑 10 秒自动保存间隔保持原样；其他无关工作区修改保留。没有提交业务代码到 TFS，也没有重启或发布服务。
